## 📖 使い方

点滅は光過敏性発作（PSE）や体調不良の原因になり得ます。周囲の人にも配慮し、不調を感じたら停止してください。低速・低コントラストでも安全を保証するものではありません。作者は悪用を勧めません。

1. 2台でデモを開き、どちらも「モノクロ」にする。受信映像を見ながら明るさを調整し、反射を避ける。
2. 受信側を「受けるだけ」にし、「カメラをテスト」を押してカメラを許可する。名前、解像度、取得fpsと映像を確認する。プレビューがオフなら「映像を表示する」をオンにする。
3. カメラが複数ある場合は「使うカメラ」で選ぶ。テスト中にも切り替えられる。接続したカメラが見つからなければ「一覧を更新」を押す。
4. 受信側で「受信開始」を押す。送信画面の発光面の内側だけが測定枠に入るよう、端末を固定する。
5. 送信側を「送るだけ」にし、まず`A`を入力して開始する。③→②→①→開始の後に送信する。初期設定で準備3秒＋送信51秒。受信側を先に開始し、120秒の受信制限内に送信を終える。
6. ライブ文字とグラフを観察する。最後にCRCと終了マーカー・UTF-8を確認する。不成功の文字列は未確認として扱う。
7. 「停止」で中断する。「表示を消去」で結果と測定値を消す。

「受けるだけ」を選んだ時点ではカメラも信号の表示も始まりません。「受信開始」を押して許可すると映像・グラフ・ライブ復号を開始します。「映像を表示する」がオフなら映像だけを隠します。広い画面では測定枠の調整欄が映像の右側にあり、狭い画面では映像・ライブ復号・グラフの後に並びます。

カメラテストでは復号せず、映像が取得できるかを確認します。「テストを停止」、タブの非表示、最大120秒でカメラを解放します。テスト中の「受信開始」は同じカメラで受信を始め、受信の制限時間を数え直します。受信中のカメラ変更では前のカメラを停止し、同期と復号を最初からやり直します。カメラ名や選択した機器は保存しません。

カメラの一覧と名前は、許可前には省略される場合があります。空の一覧だけでは未接続と断定できません。テストで許可拒否、カメラなし、使用中、選んだ機器の利用不可を分けて表示します。映像の取得を確認できても、光通信の成功を保証するものではありません。

カラーを試すときは両側をカラーにします。先頭の較正を含めて受信してください。速い設定、カラー、2色、高コントラスト、動きを減らす設定での送信には確認ダイアログがあります。全画面表示や自動再送はありません。タブが隠れると停止し、自動再開しません。

1台で確認する場合は「オフライン復号」で、本ツールの送信を記録した動画を選びます。ブラウザーで再生できるMP4・WebMなど、128MiB以下・120秒以下が対象です。正解の文字列を入力した場合に限り、文字の一致率と誤り率を表示します。一般の動画から文章を抽出する機能ではありません。本ツールには録画機能がありません。

## ✨ 機能と判定の読み方

| 項目 | 内容 |
|---|---|
| 役割 | 送るだけ／受けるだけ／オフライン復号の3種類 |
| カメラ | 一覧と更新、機器の選択、映像と解像度・fpsのテスト。切り替え時は旧カメラを解放 |
| モノクロ | 暗→明が0、明→暗が1。1 bit/組（2シンボル） |
| 2色 | 青→赤が0、赤→青が1。1 bit/組。線形化した赤青比率R/(R+B)の差で判定 |
| カラー | RGBそれぞれ反転した値と組にし、計3 bit/組。黒基準とRGBの較正付き |
| 測定枠 | ドラッグまたは4本のスライダーで指定。変更時は同期を再取得 |
| グラフ | 線形化した輝度、赤青比率、または較正後RGB。組の中央を表示。線種でも区別 |
| 確信度 | 組内の差と雑音に基づく目安。正解の確率ではない |
| `?` | 確信度不足、または取得できなかったシンボルを含む文字 |
| CRC-8 | 伝送中の誤りを調べる。暗号化・送信者認証・誤り訂正ではない |
| 一致率 | オフラインで正解があるときだけ、同じ位置のUnicode文字の一致数÷長い方の文字数 |
| 環境表示 | 採取fps、rVFC/rAF、解像度、露出・WB固定のAPI報告、推定周期 |

露出は手動モードの要求後に露出時間を要求し、ホワイトバランス（WB）は別に要求します。非対応や拒否でも解析を続け、状態を表示します。プリアンブルで同期し、その後は各組の前半と後半を比較します。両方に共通する明るさ変化には対応しますが、自動調整の影響をすべて除去できるわけではありません。

### 同期と訂正を追加したv2

送受信の両端でページを再読み込みしてください。v2は旧方式の送信や録画と互換性がありません。初期値の2 symbol/sは実際に色を更新する速度です。1ビットを2シンボルにするため、8バイトはモノクロ・青赤107秒、カラー47秒です。開始前3秒は別です。

- 同じ値の連続：暗→明または青→赤が0、その逆が1。各組の中央に変化があり、直近の観測から周期と位置を更新する。
- 明るさの変化：各組の前半と後半を比較する。明暗差が雑音の6倍未満など、判定条件を満たさない組は欠落として扱う。
- 短い誤り・欠落：長さは拡張Hamming(8,4)で保護。本文・CRC・冗長部はRSの2バイト冗長により、1バイトの誤り、または位置がわかる2バイトまでの欠落を訂正する。
- 受信失敗：成功に変更せず、120秒の上限内で次の同期信号を待つ。送信側の自動再送はない。再送が上限に収まらない場合は受信も開始し直す。

訂正数とCRCを別々に表示します。ライブ文字は訂正前の途中経過で、最後に訂正される場合があります。訂正範囲を超える誤りをすべて検出できるわけではなく、CRC-8にも見逃しがあります。[符号と受信処理の詳細](docs/protocol-v2.md)を参照してください。

### 受信が安定しないとき

測定枠は点滅面より少し小さくし、枠全体が点滅面の内側に収まるよう調整してください。送信面が枠の一部に入るだけでは、背景の色が平均値に混ざります。四隅のドラッグで大きさを変更し、枠内のドラッグで移動します。枠外からドラッグすると新しい枠を作り、操作中の枠を表示します。指を離した時点で採取範囲を変更し、同期をやり直します。スライダーでも調整できます。

モノクロは明暗の差を測るため、送信画面を暗くしすぎると信号の差も縮みます。反対に、受信映像で発光面が白一色になると明暗や色の差が失われます。測定枠の調整欄に、白に近い画素、黒に近い画素、いずれかの色が上限付近の画素の割合と、直近2秒の信号の変動幅を表示します。受信側の測定値を見ながら少しずつ調整してください。これらは調整の目安で、通信の成功判定ではありません。

明暗の判定が安定しない場合は、両側で「2色（青・赤）」を選べます。赤青比率R/(R+B)では、両チャネルに同じ倍率が掛かる明るさ変化を相殺できます。同期信号から比率の2水準と周期を求めます。単なるモノクロの着色ではありません。ただし、白飛び、暗部の雑音、背景光の変化、色の自動補正は残ります。CRC不一致を成功に変える機能ではありません。2色の速度はモノクロと同じです。

iPhoneでは画面全体の明るさを変更します。True Tone・Night Shift・明るさの自動調節も表示を変えるため、比較実験では設定を記録し、一時的にオフにして条件をそろえる方法があります。操作は[Appleの公式説明](https://support.apple.com/en-us/109351)を参照してください。本ツールには端末の画面輝度を固定する機能はありません。カメラの手動露出・WBもブラウザーが対応を報告した場合に要求するだけです。

v2でも、モノクロ・青赤ともに「復号中になるが成功しない」と本人から報告されています。実機の測定値をまだ採取していないため原因未特定です。iPhone実機、Vivaldi、物理カメラ複数台、2台間の距離・環境光・露出/WB固定の実効は本人確認待ちです。

グラフの上に、受信の残り時間・採取フレーム数・停止理由を表示します。受信成功または120秒で測定を停止し、停止時のグラフを残します。送信側だけを再送しても受信は再開しません。「受信を再開」を押してから送信してください。

失敗箇所の調査には、グラフ下の「受信失敗の診断」から「受信診断を保存」を使います。測定時刻・RGB平均値・判定経過をJSONで端末内に保存し、画像・音声・カメラ名・機器ID・動画のファイル名は含めません。測定値から送信内容を復元できる場合があるため、共有する場合は`A`などのテスト文字を使ってください。診断は次の送受信開始・表示の消去・再読み込みで消えるため、再試行の前に保存します。

## 🔬 転送速度の限界と密度

カメラのフレームレートが速度を制限します。1シンボルに複数のフレームが必要で、本ツールは同期時に2 frame/symbol未満を拒否します。30fpsならシンボルレート15 symbol/s以下が必要条件であり、十分条件ではありません。露出時間、フレーム欠落、画面更新との位相差、距離、環境光、露出・WBの自動調整でさらに条件が厳しくなります。

カメラで画面全体の明滅を1チャネルとして読む方式は、モノクロで数bps〜数十bps級の設計になります。本実装の選択肢は2/4/8 symbol/sなので、反転した値を送る時間も含め、符号ビットの速度はモノクロと2色が1〜4 bit/s、カラー3〜12 bit/sです。高速フォトダイオードやローリングシャッターの縞を読む方式の限界を表すものではありません。

次表は最大8バイトを送る計算値です。モノクロは`mono`、青赤2色は`bicolor`、カラーは`color`と表記します。実効速度は本文64ビット÷送信時間で、プリアンブル・符号化した長さ・CRC・誤り訂正・反転送信・終了マーカー・色較正を含みます。実機の測定値ではありません。開始前のカウントダウン3秒は次表の送信時間に含みません。

| モード | symbol/s | 符号ビット速度(bit/s) | 8バイトの時間(s) | 本文の実効速度(bit/s) |
|---|---:|---:|---:|---:|
| mono | 2 | 1 | 107 | 0.6 |
| mono | 4 | 2 | 53.5 | 1.2 |
| mono | 8 | 4 | 26.75 | 2.39 |
| bicolor | 2 | 1 | 107 | 0.6 |
| bicolor | 4 | 2 | 53.5 | 1.2 |
| bicolor | 8 | 4 | 26.75 | 2.39 |
| color | 2 | 3 | 47 | 1.36 |
| color | 4 | 6 | 23.5 | 2.72 |
| color | 8 | 12 | 11.75 | 5.45 |

カラーは較正分の時間があるため、短文の所要時間はモノクロの単純な3分の1にはなりません。4段PAMは純関数の比較試験だけに残し、UIには公開していません。[旧方式の合成比較値](docs/measurements.json)は互換処理の回帰検査です。v2の性能や実機成功率ではありません。

密度を増やす方法には、時間だけでなく空間を使う選択もあります。v2のモノクロは2シンボルで1ビット、RGB並列は2シンボルで3ビットですが、QR Version 1-Lは1枚で最大17バイト＝136ビット（バイトモード）を格納できます。QRは位置検出用パターン、Version 2以降のアライメントパターン、Reed-Solomon訂正を使います。L/M/Q/Hの約7/15/25/30%は符号語に対する復元の目安で、画像の同じ面積が必ず復元できる意味ではありません。実用の画面間転送では2次元の密度が有利です。[DENSO WAVEの容量表](https://www.qrcode.com/en/about/version.html)・[誤り訂正](https://www.qrcode.com/en/about/error_correction.html)

## 🔄 他のエアギャップ通信との比較

研究ごとに送受信機と条件が異なります。距離は実験室条件・直視・特定機材などに依存し、本ツールの性能を示しません。`B/s`はバイト/秒、`bit/s`はビット/秒です。対策欄は経路を制限する例であり、それだけで防止を保証しません。

| 方式 | 経路・受信機 | 報告された帯域 | 報告された距離 | 経路を制限する例・出典 |
|---|---|---|---|---|
| Photon Flicker Link | 画面→カメラ | mono 1〜4 bit/s、color 3〜12 bit/s（冗長部を含む） | 本人確認待ち | 遮光・画面とカメラの配置管理。本実装の計算値 |
| LED-it-GO | HDD LED→フォトダイオード／カメラ | 4000 bit/s／15〜120 bit/s | 光センサー：室内3〜5m・夜間屋外20m。カメラ：8m | LEDの遮光・視線の遮断。[論文](https://arxiv.org/abs/1702.06715) |
| 音響（Day120 / ggwave参考） | スピーカー→マイク | ggwave：8〜16 B/s。Day120：1.25〜11.08 B/s（256バイト計算値） | ggwave：約1m（開発者談）。Day120：未測定 | 音響経路・マイクの管理。[ggwave](https://github.com/ggerganov/ggwave#details)・[Day120](https://github.com/ipusiron/airborne-tone-link) |
| MAGNETO / ODINI | CPU磁界→スマホ磁力計／専用磁気センサー | 0.2〜5 bit/s／40 bit/s | 0〜12cm／100〜150cm | 距離・磁気センサーの管理。[MAGNETO論文](https://arxiv.org/abs/1802.02317)。ODINI値は同論文の表経由、原論文未確認 |
| BitWhisper | 発熱→別のPCの温度センサー | 1〜8 bit/hour | 0〜40cm、双方向 | 端末間隔・温度変化の管理。[論文](https://arxiv.org/abs/1503.07919) |
| AirHopper | ビデオカード→FM受信携帯 | 13〜60 B/s | 1〜7m | 電磁遮蔽・受信機の管理。[研究機関](https://cyber.bgu.ac.il/how-leak-sensitive-data-isolated-computer-air-gap-near-mobile-phone-airhopper/) |
| PowerHammer | 電力線の電流変動→電流プローブ | line-level：約1000 bit/s、phase-level：約10 bit/s | 配電線のタップ位置に依存 | 電力線側の監視・フィルター。[論文](https://arxiv.org/abs/1804.04014) |

光では監視カメラを受信機にする研究もあります。[aIR-Jumper](https://arxiv.org/abs/1709.05742)は赤外線と監視カメラの例です。可視光を透過するガラスならガラス越しの受光が可能ですが、反射・着色・遮光膜の影響を受けます。近接熱通信とは必要な配置や応答時間が異なり、熱の伝わり方を一律に扱うことはできません。

見通し（LOS）と光学系を確保すると望遠で離れた発光体を観察できます。ただしLED-it-GOの夜間屋外20mは光センサーの値で、カメラの値と分けて読む必要があります。光は音響ノイズの直接の影響を受けにくい一方、太陽光・照明の100/120Hzフリッカー・反射・別の発光が雑音になります。

## 🎯 ユースケース

このツールならではの使い方

- 情報教育の授業で、`A`（1バイト・51秒）、`LIGHT`（5バイト・83秒）、`日本`（6バイト・91秒）を比較し、「文字数」と「UTF-8のバイト数」が転送時間に与える差を調べる。すべてモノクロ・2 symbol/sでの計算値であり、開始前3秒は別である。
- 通信設計の学習で、8バイトのモノクロ107秒とカラー47秒を比較し、並列化の利得から較正のコストを読み取る。実際の成功率は色の分離や環境光にも依存する。
- 映像制作の担当者が、同じ動画の測定枠を発光面の内側と背景込みで変え、組内の差と確信度の変化を観察する。RGB値はカメラ画像の相対値で、照度計や測色計の代用ではない。
- 謎解きの制作者が、短い合図`LIGHT`を送って復号過程を見せる。暗号化がないため、方式を知る人は復元でき、秘密の合言葉の保護にはならない。

一般的な学習・制作での利用

- 家庭や工作会で、受信開始、端末の固定、停止を分担し、離れた端末に文字を渡す実験を行う。周囲の人の同意と点滅への配慮が必要である。
- 研究の予備実験で、同じ短文を距離・照明・端末を変えて受信し、条件とCRC結果を別途記録する。本ツールは動画や受信結果を自動保存しない。
- Day120の音響経路、Day041の音の帯域観察と組み合わせ、媒体ごとに受信条件が異なることを学ぶ。光の信号をDay041で測ることはできない。

## 🔒 データと安全対策

映像はフレームごとにcanvasで処理し、録画しません。選んだ動画のblob URLは停止・完了時に解放します。文字列・グラフはページ内のメモリーにだけ残り、「表示を消去」またはページを閉じると消えます。localStorageに保存するのは言語と明暗だけです。

「受信診断を保存」を押した場合だけ、測定値と判定経過をJSONファイルとしてダウンロードします。自動アップロードはありません。ダウンロードしたファイルはページの消去後も端末内に残ります。

アプリの解析処理は外部通信を行いません。CSPは`connect-src 'none'`を維持し、ローカル動画用に`media-src 'self' blob:`を指定しています。インラインスクリプト・style属性・外部ライブラリーを使いません。公開ページの初回取得と、自分で開いた外部リンクの通信は別です。

暗号化がないため、方式を知る受信者は内容を復元できます。covert channelが隠そうとするのは通信の存在や媒体であり、内容の秘匿を保証するものではありません。本ツールの低速の点滅も、人に気づかれないとは限りません。

GitHub Pagesでは任意のHTTPヘッダーを設定できず、X-Frame-OptionsとCSPのframe-ancestorsはmetaでは適用できません。

## 💻 動作環境

JavaScriptとCanvasを使うブラウザーが必要です。送信・座学・オフライン復号のUIは`index.html`を直接開いても動作します。カメラはHTTPSまたはlocalhostで利用し、ブラウザーの許可が必要です。ローカルHTTPは`python -m http.server 8000 --bind 127.0.0.1`で起動できます。

rVFCがあれば動画フレームの時刻を使い、なければrAFで採取します。rAFの時刻とfpsは近似値で、rVFCと同じ精度を保証しません。カメラ・コーデック・露出/WBの対応状況は端末ごとに異なります。ChromiumとFirefoxでUIと送信開始から自動終了までの全発光色を検証し、動画・仮想カメラの受信検証はChromiumで実施しています。Safari実機は未検証です。
