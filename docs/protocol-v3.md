# Photon Flicker Link v3 通信仕様

v3は、グレースケールの明暗対と専用クロックで1ビットずつ送る時系列の光通信です。
初期値は2 symbol/s、低コントラスト、本文はUTF-8最大8バイトです。
旧v1/v2の録画と互換性はなく、送受信の両端で同じ版を使います。

## 空間の使い方とQR転送との違い

送信パネルには横並びの4本の帯を表示します。
左の2本がデータ、その右の2本がクロックです。
各対は明と暗を同時に表示し、受信側は同じカメラ画像内の差を読みます。
これにより、異なる時刻の画面を比較する際の露出変化を減らす設計です。

本文のデータは、1回の表示につき1ビットだけです。
同じビットが続いても、専用クロックは毎回反転します。
短文の復元には表示の時系列が必要で、1枚の画像に本文を格納しません。
固定枠は位置と明暗の基準に使い、データのセル配列ではありません。
QR、連続QR、カラーコード、独自の2次元バーコードによる転送は採用しません。

| 左からの帯 | 内容 | 0 | 1 |
|---|---|---|---|
| 1 | データ | 暗 | 明 |
| 2 | データの補数 | 明 | 暗 |
| 3 | クロック | 暗 | 明 |
| 4 | クロックの補数 | 明 | 暗 |

時刻番号を0から数え、クロックを番号の下位1ビットとします。
帯の論理値は`[data, 1-data, clock, 1-clock]`で、合計は常に2です。
4本を等面積にしているため、各更新でパネルの平均的な明るさを保ちます。
反射、画面のPWM、撮像の非線形処理、空間的に異なる露出や雑音までは相殺できません。

## パネルと画像の読み取り

基準のパネルは640×240px、縦横比8:3です。
外周は線形輝度0.85、その16px内側から608×208pxを0.015で描きます。
各帯は左端x=32、180、328、476px、上端y=32px、幅132px、高さ176pxです。
通常の帯の低値と高値は0.18/0.32、高コントラストは0.06/0.60です。
描画時にsRGB値へ変換します。停止時の4本はすべて0.25で静止します。

探索範囲には固定枠を含むパネル全体を入れます。
受信画像を線形化し、輝度係数0.2126/0.7152/0.0722でRGBを合成します。
暗い連結領域の候補を探し、四角形と上下の白黒枠を検査します。
連結領域の粗い探索後、枠と帯の測定には元の画像の画素を使います。
固定枠が複数見つかった場合は、以前のパネルをそのまま信頼せず、そのフレームを拒否します。

受け付ける形には次の制限があります。値は撮像後の解析用画像に対するものです。

- 暗い枠の長辺が90px以上、短辺が30px以上
- 長辺と短辺の比が2.2〜3.8
- 上下辺の長さの比と左右辺の長さの比が、それぞれ0.75以上
- 主軸の傾きが±15度以内
- 外側の枠が探索範囲に収まり、必要な基準点を取得できること

これらの境界内でも、検出や復号の成功は保証しません。
強い遠近変形、回転、部分的な遮蔽、ぼけ、白飛び、小さい像は対象外です。
画面上の見かけの角度だけでなく、実際に枠と帯を測れる必要があります。
上下を正しくして4本を横に並べてください。180度の回転や左右反転は自動補正しません。

1か所の測定では7行×5列の35点を読みます。
中央値からの偏差の中央値に1.4826を掛けて雑音の目安とし、上下7点ずつを除く21点の平均を測定値とします。
5か所の黒基準と2か所の白基準を横方向に補間し、各帯の値を次式で補正します。

```text
normalized[i] = (measured[i] - blackReference[i]) / (whiteReference[i] - blackReference[i])
data  = clamp(normalized[0] - normalized[1], -1, 1)
clock = clamp(normalized[2] - normalized[3], -1, 1)
```

基準の白黒差には0.025以上が必要です。
上下枠の基準からのずれは基準差の18%以下、雑音は12%以下とします。
各帯の補正値が−0.05〜1.05から外れた場合も拒否します。
対の生の輝度差が`max(0.002, 6×雑音)`未満、または補正後の差が0.04未満なら品質は0です。
それ以外は`clamp(abs(補正後の差)/0.15)`を、その対の品質とします。
データ品質とクロック品質は別々に保持し、画面表示用の全体品質だけに小さい方を使います。
データの差が消えてもクロックを読める場合は区切りを保持し、そのビットを欠落としてRSへ渡します。

固定枠を検出できたことと、データを読めることは別です。
停止時のパネルは枠を検出できますが、4本が同じ明るさなので品質は0です。

## フレーム構造

本文のバイト長をL、ブロック数を`B = max(1, ceil(L/4))`とします。
0〜4バイトは1ブロック、5〜8バイトは2ブロックです。
空の本文も1ブロックを送ります。

各ブロックを次の順番で送ります。バイトは上位ビットから送信します。

| 項目 | 長さ | 内容 |
|---|---:|---|
| 同期列 | 16ビット | `1101010011000101` |
| ヘッダー | 16ビット | 1バイトを上位/下位4ビットに分け、それぞれHamming符号化 |
| 全体識別情報 | 2バイト | 全体CRC-16の上位バイト、下位バイト |
| ブロック本文 | 0〜4バイト | 本文の該当部分 |
| ブロックCRC | 1バイト | 復号後ヘッダー、識別情報、ブロック本文に対するCRC-8 |
| RS冗長部 | 2バイト | 識別情報、ブロック本文、ブロックCRCを保護 |

符号化前のヘッダーは`0xA0 | (blockIndex << 4) | L`です。
ブロック番号は0または1で、上位4ビットはそれぞれAまたはBです。
長さが4以下で番号1を受けた場合は拒否します。

ブロック間に専用の終了マーカーは置きません。
最後のブロックの後に、データ値0のガードを2更新分付けます。
ガードも専用クロックを反転し、最終データビットの区切りを確定する役割があります。
ガードのデータ色そのものを成功条件にはしません。
既知の長さと各CRCで完了を判定するため、未保護の終了色だけで受信全体を破棄しません。

## CRCと誤り訂正

### CRC-8

CRC-8/SMBUSと同じパラメーターを使います。
多項式は0x07、初期値0、ビット反転なし、最後のXORなし、上位ビットから処理します。
入力は符号化前ヘッダー、全体識別情報2バイト、ブロック本文の順です。
ASCIIの`123456789`に対する既知解答は0xF4です。

### CRC-16

全体識別情報はCRC-16/CCITT-FALSEのパラメーターで計算します。
多項式は0x1021、初期値0xFFFF、ビット反転なし、最後のXORなしです。
入力は本文長の1バイトと本文全体です。
ASCIIの`123456789`は0x29B1、空の配列は0xFFFF、`[0]`は0xE1F0になります。

CRCは偶発的な伝送誤りの検査です。
暗号化、送信者認証、改変防止を提供せず、誤りの見逃しや異なる本文の衝突もあります。

### 拡張Hamming(8,4)

上位4ビットと下位4ビットを別々に保護します。
1から数えた位置1/2/4/8が検査ビットです。
候補の符号語に対する誤り数eと欠落数sが`2e+s < 4`を満たす候補を探し、唯一の候補だけを受け付けます。
1つの8ビット符号語で1ビット誤り、または3ビットまでの既知の欠落を訂正できます。
誤りと欠落を最大数ずつ同時に訂正できる意味ではありません。

| 元の4ビット | 送信する8ビット |
|---|---|
| 0 | `00000000` |
| 1 | `11010010` |
| 5 | `01001011` |
| A | `10110100` |
| B | `01100110` |
| F | `11111111` |

### 2バイト冗長のRS

GF(256)で原始多項式0x11D、原始元2を使います。
符号語を`c[0]...c[n-1]`とし、`XOR(c[i])=0`と`XOR(alpha^i*c[i])=0`になる2バイトを末尾に付けます。
保護する対象は全体識別情報、ブロック本文、ブロックCRCです。

1ブロックについて、1バイト誤り、または位置がわかる2バイトまでの欠落を訂正できます。
不明ビットを含むバイトは、そのバイト全体を欠落として扱います。
3つ目の欠落バイトが確定した時点でそのブロックを破棄し、残りを待ちません。
訂正後もブロックCRCを確認し、能力を超えた入力が常に検出できるとは説明しません。

### 送信例

`A`の本文は`41`、長さは1、全体識別情報は`76 DB`です。
ヘッダーは`A1`で、Hamming符号化すると`10110100 11010010`です。
同期列とヘッダーの後には、RS冗長部を含む`76 DB 41 1E 6B 99`を送ります。
このブロックは80更新、最後のガードを含め82更新、2 symbol/sで41秒です。

`LIGHT`は長さ5、全体識別情報は`4C 90`です。
ブロック0のヘッダーは`A5`、本文は`4C 49 47 48`、符号語は`4C 90 4C 49 47 48 B9 6D 02`です。
ブロック1のヘッダーは`B5`、本文は`54`、符号語は`4C 90 54 E0 26 4E`です。
各ブロックは104更新と80更新、最後のガードを含め186更新、2 symbol/sで93秒です。

## クロックとビットの判定

受信側の設定速度は送信側へ合わせる必要がなく、観測した専用クロックから周期を求めます。
入力時刻は単調増加の有限値に限ります。
パネルが見つかり、クロック品質0.45以上、クロック差の絶対値0.025以上のフレームで区切りを読みます。
データ品質の不足だけではクロックの観測を捨てません。

クロックの反転は、反対の値が2フレーム続いた場合に確定します。
途中で元の値へ戻れば候補を取り消します。
同じクロック値の区間には最低2フレームが必要です。
5フレーム以上ある場合は先頭と末尾を除き、残りのデータ差の中央値を取ります。
データ差の絶対値0.025以上、符号が一致するフレームが選択数の3分の2以上であることを確認します。
さらに、選択したデータ品質の中央値に符号の一致率を掛けた確信度が0.45以上ならビットを確定します。
不足する場合は、そのビットを欠落とします。

カメラは境界そのものを撮影するとは限りません。
変化位置を「最後に旧値を撮った時刻〜最初に新値を撮った時刻」の区間として扱います。
開始境界を`[startLow, startHigh]`、終了境界を`[endLow, endHigh]`とすると、周期の範囲は次のとおりです。

```text
periodLow  = endLow  - startHigh
periodHigh = endHigh - startLow
period     = midpoint(endLow, endHigh) - midpoint(startLow, startHigh)
```

隣接する2区間の平均を求め、その中央値を周期の推定値にします。
履歴は直近8区間で、4区間を観測してから周期の検査を始めます。
観測した周期の範囲が推定周期の0.5〜1.65倍と重ならない場合は同期を破棄します。
境界の不確かさを区間で扱うため、最初の新値フレームだけを境界時刻とする判定はしません。

有効なフレームの間隔が推定周期の0.8倍を超えた場合も同期を破棄します。
クロックが変化せず1.65周期を超えた場合は古いブロックを捨てます。
周期変更時には実際に観測した区間を保持して新しい同期を探しますが、取り逃した区切りの数を推測して補いません。

## 同期の再取得とブロックの組み立て

復号中も直近16ビットから同期列を探し、最大8個の候補を処理します。
同期列が本文内に偶然現れる場合もあるため、候補のヘッダー、RS、CRCを検査します。
表示中の有効な候補がある場合、同期列だけを見つけた別候補へ即座に表示を切り替えません。
新しい候補の保護されたヘッダーを確認してから表示を更新します。

検査済みブロックは、本文長と全体CRC-16の組をキーとして保持します。
組み立て中のメッセージは最大4件で、上限を超えると最も古いものを削除します。
同じキーと番号の重複は1回として数え、内容が異なる場合はその組み立てを破棄します。
同期を失っても検査済みのブロックは保持するため、同じ内容の再送から不足したブロックを補えます。

すべてのブロックがそろったら番号順に連結し、全体CRC-16と厳密なUTF-8を確認します。
双方が成功したときだけ最終結果を成功とします。
ライブ文字は先頭から連続してそろった検査済みブロックを表示し、後半だけでは本文を確定しません。
識別情報は16ビットのCRCなので衝突があり、別の通信を絶対に混ぜない保証や認証は提供しません。

## 所要時間と入出力の上限

本文長L、ブロック数B、更新速度Rに対する計算値は次式です。

```text
updates = 72*B + 8*L + 2
seconds = updates / R
B = max(1, ceil(L/4))
```

2 symbol/sでは空本文37秒、Aは41秒、LIGHTは93秒、最大8バイトは105秒です。
送信前の3秒カウントダウンは別です。
各表示の保持時間は実際の描画命令の実行時刻で測り、次の更新はその時刻から1周期後に行います。
遅れた後に次の表示を短くして追いつくことはありません。
保持が規定周期の120%を超えると送信を中止し、送信完了を返しません。
ブラウザー内の描画時刻は、ディスプレイの実発光時刻を測った値ではありません。

カメラの起動待ちは最大30秒、ライブ受信は最初の採取フレームから最大240秒です。
ローカル動画は120秒、128MiB以下に制限し、再生開始後の期限も120秒です。
再同期で期限を延長せず、成功、停止、非表示、期限到達時に撮像資源を解放します。
受信開始時に露出やWBを自動で手動へ変更しません。

rVFCでは提示フレーム番号とmediaTimeの進行を使います。
ライブのmediaTimeが止まる場合、同一フレームで対応づけた撮像時刻または提示時刻を使用します。
rAFでは先に動画をcanvasへ描き、その後にフレーム数を検査します。
ライブ映像で`webkitDecodedFrameCount`が取得できる場合は、その復号済みフレーム数の進行を使います。
非表示ライブ映像の`droppedVideoFrames`には、canvasからは読めるが描画合成では提示されなかったフレームも含まれます。
そのため、総数から欠落数を引くだけではライブ映像の更新停止を正しく判断できない場合があります。
復号済み数が既知で変化していない場合は、currentTimeだけを理由に別のフレームとして採取しません。
ファイルでは復号済みフレームが再生位置より先行するため、このライブ用の値を使いません。
復号済み数を使わないrAF経路では`totalVideoFrames-droppedVideoFrames`を、フレーム数APIがない場合はcurrentTimeの進行を使います。
rAFの時刻は撮像時刻そのものではなく、rVFCと同じ精度を保証しません。

受信診断の測定列は、時刻、データ差、クロック差、データ品質、クロック品質、パネル検出の6項目です。
画像、音声、機器名、機器IDを含めず、明示操作で端末内のJSONへ保存します。
測定列から本文を復元できる場合があるため、共有時はテスト文字を使います。

## English overview

V3 is a serial optical channel carrying one payload bit per display step.
Two grayscale bars encode data and its complement; two more encode an independent clock and its complement.
The fixed frame provides geometry and brightness references, not a spatial payload grid.
QR, animated QR, color codes and custom two-dimensional barcode transfer are excluded.

Payload chunks contain up to four bytes, with a Hamming-protected header, whole-message CRC-16 identity,
block CRC-8 and two Reed-Solomon parity bytes. The receiver keeps checked blocks across resynchronization,
but accepts the final text only after whole-message CRC-16 and strict UTF-8 checks.
Camera-edge times are intervals between old and new observations, and missing transitions are not invented.
The 240-second live deadline begins with the first sampled frame; opening is limited separately to 30 seconds.
Physical iPhone-to-PC/Vivaldi reliability remains awaiting owner testing.
